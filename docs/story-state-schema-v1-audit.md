# Compatibility Assessment: Canonical Story State Schema (v1) vs. shipped step-1 container

> Audited 2026-07-26 against the shipped Works/Project container (productization step 1:
> ggbc-backend PR #39 / frontend PR #312) — backend at migration head `0012_lovense_multi_pairing`,
> frontend `main` at `5d60464`. The schema doc under audit is
> [story-state-schema-v1.md](story-state-schema-v1.md). Section 3 is the ordered step-2 gap list.

## 1. CONFLICTS — shipped implementation actively contradicts the doc

**C1. ID/reference model: doc demands stable UUIDs; the platform's identity model is mutable strings.**
Doc principle 8 ("Stable IDs. Every entity, scene, fact... gets a UUID and keeps it," line 18) and the ingestion fields `meta.source.character_card_ids`, `session_ids`, `persona_id` (lines 49-52) and `characters[].source_card_id` (line 118) assume ID-addressable source objects. The shipped contract is the opposite: characters are identified by avatar filename strings ("Ivy.png") and chats by the `(character_avatar, file_name)` tuple; chat/character UUIDs are deliberately internal-only (model docstring, `/Users/sammy/Documents/GitHub/ggbc-backend/app/models/project.py:30-36`; `app/models/chat.py:23-27` "instead of exposing the UUID"; schema docstring `app/schemas/project.py:1-8`). Worse for the doc: these string refs **may dangle after delete/rename and the frontend reconciles** (project.py:33-35). A bible whose provenance links hang off `source_card_id` breaks silently on character rename — directly violating principle 7 ("provenance survives updates"). The doc's ingestion table ("link back to ST character card") has no stable thing to link to.

**C2. `msg_id` provenance has no referent — ST messages carry no IDs.**
The doc leans on message-level addressing everywhere: `scenes[].source.message_range: [msg_id_start, msg_id_end]` (line 262), `swipe_resolutions[].msg_id` (line 265), `excluded_segments` (lines 268-271), `continuity.fact_log[].source_msg` (line 301), `characters[].provenance.chat_evidence: [msg_id]` (line 167). The shipped chat store (`app/models/chat.py:43-45`) is a JSONB array of ST-format message dicts with a header object as element 0 — ST messages have no UUIDs; the only stable-ish handle is array index, which shifts on deletion/regeneration and is offset by the header convention. There is no message-ID space for the doc's provenance model to point into. This is the deepest schema/reality mismatch: either step 2 adds message IDs to the chat format (a chat-storage migration + frontend change), or every `msg_id` field in the doc must be respecified as index-or-hash-based addressing with staleness semantics.

**C3. Storage "open decision" is already foreclosed for v1.**
Open decision 1 (line 487) treats storage as undecided and leans "Postgres + pgvector... transactional integrity matters for the edit log." What shipped is a single opaque JSONB column (`story_state JSONB NOT NULL DEFAULT '{}'::jsonb`, migration `0011_add_projects.py:51-56`, model project.py:72-74) with **full-document replace** on PATCH (`row.story_state = payload.story_state`, `app/routers/projects.py:156-157`) — no relational entities, no append-only tables, no pgvector (zero hits for vector/embed in migrations/, models/, pyproject.toml; migration head is 0012, no extension created). Consequences the doc doesn't account for:
- `edit_log` and `fact_log` are described as append-only, but a full-replace blob gives **no append-only guarantee** — any client PATCH can rewrite history. "Transactional integrity for the edit log" does not exist in the shipped write path.
- The RAG-selective renderer reads ("does NOT pull the entire bible," line 427; "RAG over rule text vs. scene content," line 423) are impossible against the shipped API: `GET /projects/{id}` returns the whole `story_state` or nothing; there is no sub-document read, no embedding store.

**C4. Concurrency: five-pass incremental ingestion vs. whole-blob optional-token replace.**
The doc's ingestion is "five distinct agent passes" (line 413) plus round-trip edits — many writers incrementally enriching one document. The shipped write path is wholesale replace guarded only by an **optional** `base_ts` (`app/schemas/project.py:50`; router projects.py:135-142); a PATCH omitting `base_ts` clobbers unconditionally. The frontend's retry helper (`useProjectStore.updateSelected`, `goodgirlsbotclub/src/stores/projectStore.ts:142-179`) retries once and adopts the winner wholesale — fine for name/description edits, lossy for concurrent agent passes each carrying a multi-MB bible. Doc has no merge strategy; the platform provides none.

**C5. Bible grain: single-session-per-bible vs. multi-chat container.**
The doc's v1 cut says "Multi-session merging. Single source session per bible" (line 475), yet `story_state` lives on a Project whose entire purpose is to "group chats + characters **across sessions**" (project.py:26-28), and `chats` is a list. The container invites attaching chat #2; the doc forbids ingesting it. Meanwhile `meta.source.session_ids` is plural (line 49) — see D1. Step 2 must define what happens when a project has 3 chats attached and the bible supports 1 (ingest first? force a picker? per-chat bibles?). The doc is silent.

**C6. Doc's session/persona ID types don't match GGBC's.**
`session_ids: [array] # ST chat IDs / GGBC session IDs` — GGBC "session ID" in the shipped system is the `(character_avatar, file_name)` tuple (`ProjectChatRef`, schemas 20-25), not a scalar ID. `persona_id: string` — personas in the ST-style frontend are keyed by persona avatar/name strings, not IDs. The `meta.source` block needs to be respecified in the platform's actual identity vocabulary.

## 2. ACCOMMODATED — what the container already supports as-is

- **Arbitrary nested document.** `story_state` is JSONB `dict[str, Any]` with no shape validation, no size cap, no depth limit anywhere (no body-size middleware in the app; only proxy/Postgres ~255MB limits). The full `story_bible` YAML tree — scenes array, nested `entities.characters`, `rendering_hints`, `edit_log` — round-trips today verbatim (pinned by `tests/test_projects.py:97-119`).
- **Top-level-object requirement matches.** Doc's root is a mapping (`story_bible:` keys); Pydantic requires a dict at top level. Compatible. (Recommend nesting under a `story_bible` key so future siblings can coexist.)
- **Reserved slot is real and empty.** Create hardcodes `{}` (router projects.py:103); no UI reads or writes it — the only two frontend references are type declarations (`client.ts:1614, 1627`). Step 2 can define the schema with zero pre-existing structured blobs to migrate *from the app's own writes* (though see G1 caveat — API clients could have written anything).
- **Write authorization exists.** `project:manage` gates writes, held by all four seed groups (migration 0011 backfill), owner-scoped (`Project.user_id == caller`), cross-user PATCH → 404. A step-2 ingestion agent acting as the user can write the bible with no new permission plumbing (though a bible-specific permission may be wanted later).
- **Optimistic concurrency + conflict payload.** `base_ts`/`server_ts`/409-with-full-current (`ProjectConflictDetail`, schemas 84-90) gives step 2 a stale-write detector and a merge substrate for free — necessary though not sufficient (C4).
- **Doc's renderer/deliverable framing matches `deliverable_type`.** novel / comic / video_series map to the doc's novel / graphic_novel / storyboard hint families; `freeform` = doc's "none yet."
- **`content_rating` field aligns with the existing NSFW scope policy** (fictional-characters-only) — a natural place to hang the gate.
- **List-view hygiene.** `ProjectListItem` already omits `story_state` (schemas 69-81), so a multi-MB bible won't bloat the sidebar fetch (`Sidebar.tsx:103`).

## 3. GAPS FOR STEP 2 — ordered by what must come first

1. **Message identity (blocking almost everything).** Add stable per-message IDs to the chat message format (or specify a content-hash/index addressing scheme with drift rules). Without this, `scenes.source`, `fact_log.source_msg`, `chat_evidence`, and swipe resolution are unimplementable. Touches chat JSONB shape, frontend chat writer, and possibly a backfill migration.
2. **Schema definition + validation layer.** Pydantic models for `story_bible` (per the doc's own line 497 note), wired into `ProjectUpdateIn.story_state` (or a new sub-resource). Includes deciding envelope (`{"story_bible": {...}}`), `schema_version` handling, and reference-integrity checks (`pov_character` ∈ characters, `scene_range` valid). Today validation is literally "is a dict" (schemas 49).
3. **Sub-resource write API / merge semantics.** Full-replace PATCH cannot support five agent passes + user edits. Either sub-path endpoints (e.g. `PATCH /projects/{id}/story/scenes/{scene_id}`), JSON Merge Patch, or server-side section-level merge with mandatory `base_ts`. Also: enforce append-only on `fact_log`/`edit_log` server-side — a client-writable blob cannot self-certify append-only.
4. **Ingestion passes (the five agents).** Cold-start card/lorebook parse → transcript walk (OOC strip, swipe resolve, scene detect, fact extract, voice sample) → reconcile/auditor → annotate → review checkpoint. Nothing exists; also requires the backend to read chats server-side (it has them in `chats.messages`) or a frontend-orchestrated pipeline. Note: lorebook "fired/not-fired" state (ingestion table lines 390-392) isn't recorded anywhere today — trigger telemetry must be captured at chat time or re-simulated.
5. **Contradiction surfacing UX.** `continuity.contradictions` objects + the "user review checkpoint / lock canon" flow. WorksPanel currently renders only name/description/type/members.
6. **Edit_log + round-trip diff/classify/propagate.** Depends on 2-4; the renderer must exist before rendered-output edits can round-trip.
7. **pgvector / embedding store.** Needed only when renderers go RAG-selective (line 423-427). Requires: `CREATE EXTENSION vector` migration (none of 0001-0012 create any extension), an embedding dependency (none in pyproject.toml), and side tables keyed to scene/rule UUIDs — the first step-2 feature that cannot live inside the JSONB blob.
8. **Renderer plumbing.** The transformation chains (lines 431-452), `rendering_hints` consumption, `character_consistency_refs` image handoff (note: value type `image_url` — clarify against self-hosted asset storage).
9. **Size governance.** `dialogue_examples`, `sample_passages` (5-10 verbatim passages), `detailed_summary` per scene, plus append-only logs will grow the blob; with `GET /projects/{id}` returning it whole and zustand storing it verbatim, a long RP's bible becomes a per-open megabyte download. Needs either sub-resource reads or an explicit size budget.

## 4. DOC ISSUES — flag to the author

- **D1. v1 cuts leak into required fields.** `meta.source.session_ids` is an array (line 49) and group chats are in the ingestion table (line 398), but v1 cuts single-source-session (line 475). Either make it a scalar `session_ref` for v1 or state that the array is length-1 until multi-session lands. Same tension with the multi-chat Project container (C5).
- **D2. `msg_id`, `chat_msg_id`, `place_uuid`, `image_url` are undefined types.** They read as if an ID space exists; none does (C2). A Pydantic conversion will force a decision the doc hasn't made.
- **D3. Two enum vocabularies for the same concept.** `scenes[].function.beat` uses inciting/rising/midpoint/crisis/climax/denouement/interlude (line 256) while `narrative.acts[].beat_function` is free string (line 224); `continuity.fact_log[].category: enum` (line 299) is never enumerated, while `scenes[].continuity_facts_established[].category` enumerates reveal/introduction/change/world_rule (line 277) — are these the same enum? Pydantic needs one answer.
- **D4. Duplicated facts, no single source of truth.** Facts appear both in `scenes[].continuity_facts_established` and `continuity.fact_log`; relationships' `arc_beats` duplicate `arc.beats`; `pov_default`/`tense_default` live in both `narrative` and `rendering_hints.novel`. Specify which is canonical and which is a derived index, or the full-replace write path (C4) will let them diverge.
- **D5. `pov_default: enum` (line 228) has no values**, while `pov_preferences` and `rendering_hints.novel.pov` each define different POV enums ("second-present"/"first-past"/"third-mixed" vs "first"/"third_limited"/"third_omniscient"). Three POV vocabularies; pick one or define mappings.
- **D6. Confidence is triple-typed.** Discrete enum on facts/rules (lines 94, 302), continuous float on `user_voice.confidence` (line 206) and `narrative.detection_confidence` (line 219) — while open decision 4 presents discrete-vs-continuous as unresolved. The schema already uses both; the "open decision" is misleading.
- **D7. "Append-only" fact_log and edit_log are aspirations, not properties**, given the shipped full-replace blob (C3). The doc should either require server-enforced append semantics or drop the word.
- **D8. `derivative_flags` + `content_rating` interplay with the shipped NSFW policy** (fictional-only, NCII red line) is unaddressed — worth one sentence on whether `content_rating: explicit` + `derived_from_known_ip` gates rendering.
- **D9. `rendering_hints.graphic_novel.character_consistency_refs: { char_uuid: image_url }`** — mapping-typed keys with UUID semantics are awkward in JSON Schema (patternProperties), and `image_url` conflicts with self-hosted asset policy; consider an array of `{character_ref, asset_ref}`.
- **D10. No size/pruning guidance** despite mandating verbatim passages and per-scene paragraphs; see G9. A one-line budget ("bible ≤ N KB excluding logs; logs paginated") would prevent the JSONB blob from becoming the payload problem the list-view exclusion was designed to avoid.
