# 3.3(c) Scoping — the legacy-books strip, and why the imagined backfill has no customers

**Status:** SHIPPED — the full R1-R4 package is live in production as of 2026-08-23. R1+R4: ggbc-backend #71; R2: goodgirlsbotclub #435; R3: ggbc-backend #74 (successor to the stacked #73, which GitHub auto-closed when #71's branch was deleted). Deployed in the mandated order (#71 → #435 verified live → #74), each PR adversarially reviewed pre-commit; suites at merge: 813 backend / 1441 frontend. Production-verified post-deploy: the retire-gate evaluates OPEN for both remaining blob-holders (their next hydration strips ~97 KB and ~30 KB) and no-ops for every user without a blob. Originally: scoped 2026-08-22 (adversarially reviewed against code + production data; the review materially changed the design — see the appendix). Child of `memory-consolidation-plan.md` §3.3; supersedes that section's "needs either a dedicated backfill … or enough runway" framing with measured data.

**Verdict up front:** the retroactive backfill the plan sketched — re-deriving legacy→server id pairs for already-migrated books via content matching — would serve **zero production users**. What 3.3(c) actually needs is four small changes, one of which is urgent independent of the strip: a server-side guard against blob erasure (a live data-loss window in deployed code, found during this scoping's adversarial review), a hardened frontend drop gate, the per-user gated strip itself, and an ACL on the map section. No heuristic port, no admin backfill endpoint, no flag day.

## Why the backfill has no customers

The plan's premise was: "the existing user base has no server-recorded trail and still fully depends on the heuristic fallback." Measured, that user base splits into two groups, and neither needs a backfill:

**Group 1 — migrated before step (a) (imhungryyall, sammy).** Their books were imported without pairs being recorded, but their heal is already complete: the remap + write-back machinery shipped *inside* the 2026-08-07 cutover commit (77e689d2), so every successful login since then rewrote resolvable legacy references to native ids and persisted the result (worldInfoStore.ts:2290-2337, chatLoreConfigStore.ts:676-807, characterStore.ts:944-988, personaStore.ts:423-448). The census confirms the endpoint state: zero legacy references anywhere in their sections. There is nothing left for exact pairs to resurrect.

**Group 2 — never migrated at all (mina, vulpixxy).** Both have blobs and **zero native books**, which means the per-login import (`ensureBlobImported`, worldInfoStore.ts:1918-1932, fired at the top of every `fetchPrefs` native leg) has never successfully run for them — they are dormant since before the cutover. They are not "migrated without a trail"; they are pre-migration. The trail-recording is already deployed for them prospectively: on their next login, `POST /lorebooks/import-from-blob` (bodyless — the server reads its own stored blob, lorebooks.py:869-874) inserts their books fresh, and step (a) records exact book *and* entry pairs on precisely that insert path (lorebooks.py:979-986, 1029-1039). The same session's heuristic remap still has the hydrated blob as input, so references rewrite; and the login's autosave then PUTs a books-less `stm_worldinfo` replace (`snapshotForServer` omits `books`, worldInfoStore.ts:3657-3665; PUT is a whole-value replace, sync.py:132), retiring the blob server-side.

**But the happy path above is not crash-safe — this is the urgent finding.** The books-less autosave is triggered by `fetchPrefs`' *own* state application (`set({books: nativeBooks})` at worldInfoStore.ts:3553 tripping the unconditional subscriber at 3667-3689), **not** by import or remap success. Verified interleaving under deployed code: the import POST fails transiently (`ensureBlobImported` swallows the error and continues, 1918-1932); the blob leg has already confirmed the local sync token (`recordServerTs`, 3531); `fetchNativeBooks` legitimately returns `[]` for a zero-native-book user; `set({books: []})` wipes the localStorage books cache (`saveBooks`, 3678) and ~300 ms later the autosave PUTs the books-less snapshot with a freshly-matching `base_ts` — so the 409-merge rescue (serverSettings.ts:300) never engages — and sync.py:132 erases the sole surviving copy of mina's 45 / vulpixxy's 18 entries. A second variant needs no import failure: `shouldReuploadSection` (worldInfoStore.ts:3495-3502) fires an immediate books-less PUT from a dormant dirty device that can race the import server-side. **R1 below closes this window server-side.** The same-day mitigation the review argued for — running the import server-side for the two known users (one idempotent call each against the deployed code path; the draft rejected proactive import as pointless and the review overturned that) — **was executed 2026-08-22**: both users imported cleanly with zero skips and zero validation drops (mina: 1 book, 45/45 entries, map = 1 book pair + 45 entry pairs; vulpixxy: 2 books, 10+8/18 entries, map = 2 book pairs + 18 entry pairs; map book keys verified identical to the ids her `stm_personas` references), with an off-box snapshot of both blobs taken first. The *current* cohort's erasure window is therefore closed — their next login hits the skip path with pairs already recorded, and losing the blob is now harmless. R1 remains core: it is the structural guard for any future blob (a restored backup, a 409-merge revival, a straggler device), not just these two rows.

## The other structural hazard: the confident-drop gate

`canConfidentlyDropUnresolvedLegacyIds` (worldInfoStore.ts:2046-2051) opens when this session's native `/lorebooks` fetch succeeded and shared books loaded — **it never checks that the remap had a chance**: not that inputs were available, and not that pairing succeeded. All four remap passes then permanently drop unresolved ids and persist the drop. Three verified consequences shape the design:

1. **A naive strip is data-destroying.** No blob in hydration → heuristic degrades to a clean no-op (worldInfoStore.ts:3461 short-circuits) → gate opens → every uncovered legacy reference is dropped and the drop persisted.
2. **First-session ordering.** The map is read from the *same* `getSettingsBlob` response as everything else (worldInfoStore.ts:3465-3479), *before* `ensureBlobImported` fires (3543) — pairs recorded by this session's import are invisible to this session's remap. Any strip gate must key on the map row as of the current hydration response, never on "the import will have run by now." (R3's gate does exactly this, and the review could not construct a first-session counterexample.)
3. **Input presence ≠ remap viability.** Even with the blob hydrated, an import failure leaves zero native counterparts, zero pairs, and an open gate — vulpixxy's realistic first-contact failure mode drops her persona links *with the blob present*. And no per-user mechanism can ever adjudicate a **cross-user** reference: `GET /worldinfo/shared` still serves unmigrated members' blob books with legacy ids intact (worldinfo.py:171-200, blob branch live for zero-native-row users at 238-251), any member can toggle such an id into their own `activeBookIds` (worldInfoStore.ts:3119-3126), and the owner's eventual migration makes the viewer's copy confidently-droppable. R2's per-id rule is built for both.

## Recommended package

Ship order: R1 (+R4 rider) → R2 → R3. R1 is protective and urgent; R2 hardens the client before hydration behavior changes; R3 is the strip itself.

### R1 — Server-side blob-erasure guard (backend; core; ship first)

In `put_section` (sync.py:92-136), when the target is `stm_worldinfo`, the stored row has a non-empty `books` array, and the incoming payload omits the key: evaluate the same gate as R3, and if the gate says the blob is still load-bearing, fold the stored `books` back into the written value. Symmetry is the spec: *the gate that won't strip books from a read won't let a write drop them.* Gate-open writes may drop the key — that is 3.3(c) finishing naturally at the storage layer. Costs: three extra reads (map row, native book ids, native entry ids — the last for the gate's entry arm below), incurred only on writes that would otherwise erase a live blob — i.e., a handful of logins by 2 users, decaying to zero. A payload that *includes* a `books` key (stale pre-cutover bundle) writes through unchanged, as today. Concurrency with the import is benign in both orders: fold-then-import reads the intact row; import-then-fold preserves an already-imported blob one extra cycle until the next gate-open write drops it.

Why the gate must attest more than book ids: the import can *silently drop individual entries* — `_parse_blob_entry` returns `None` for any raw entry failing `LorebookEntryIn` validation ("skip, don't 500 the import"), the entry is never inserted and never paired, yet the book's own pair still records on savepoint success (lorebooks.py:1029-1039). A book-id-only gate would open over a lossy import and let the erasing write finish the job — and this path has bitten before (`_sanitize_blob_entry_keys` exists because a stray blank key used to make the validator drop otherwise-good legacy entries). The gate's entry arm (R3) holds it closed in exactly this case: an unpaired, un-inserted entry keeps the blob alive.

### R2 — Harden the frontend drop gate to a per-id rule (frontend; core — promoted from optional by the review)

Rule: an unresolved id matching the strict legacy pattern may be **dropped only when the server map named it and its pair failed target verification** — the one case where the drop is a verified fact (the successor was deliberately deleted). Every other unresolved legacy-pattern id is **kept dangling**: blob-present-but-unpaired (import failed — retryable next login), cross-user references (never adjudicable locally), and post-strip stragglers. Dangling ids are inert — consumers only ever use id lists as filters over real books (scanMessagesForEntries chatStore.ts:1079-1082; activeIdSet membership in chatLoreView.ts / ChatLorePanel / ingestSources; worldInfoComposition's STEP C filter at 200-201) — so the cost of keeping is zero and the cost of a wrong drop is permanent. Native-format ids keep today's behavior at the drop branch (dropping references to genuinely deleted native books is correct cleanup).

Implementation is NOT a condition-tweak at the resolvers — the raw map keys don't reach them today, and the final verify pass showed a naive version silently degenerates to "never drop": `serverLegacyIdMap` is a `fetchPrefs` local (worldInfoStore.ts:3453), and `buildLegacyIdRemap` writes only *target-verified* pairs into `_legacyBookIdMap`/`_legacyEntryIdMap` (books arm 2247-2251, entries arm 2258-2266) — dead-target pairs leave no residue, and a live-target pair returns from `resolveLegacyBookId`'s first lines (2066-2067) without ever reaching the drop branch (2072). The spec is therefore:

- Capture the **raw** `serverMap.books` / `serverMap.entries` key sets into module-level state when the map is applied, alongside the filtered maps.
- Books drop branch (2072): drop iff the raw book-key set has the id (raw-named + not in `_legacyBookIdMap` ⇒ target verification failed ⇒ dead successor).
- Entries drop branch (2100): drop iff the raw entry-key set has the id **and** `_legacyEntryIdMap` does not — the entries merge validates against a deliberately *flat* cross-book id set (2258-2266), while `resolveLegacyEntryId` re-scopes to the caller's book (2097-2099); a pair whose target is alive in a *different* book must be kept dangling (inert), not dropped under a dead-target rationale.
- Clear both raw-key sets in `clearLegacyIdRemap` (2270-2272) and `resetUser` (3399-3408), following the session-scoped convention every other flag in this machinery already obeys (`_blobImportAttempted` 1918/3406, `_nativeBooksFetchSucceeded` 2011/3407) — without this, a same-tab account switch lets account A's map keys authorize permanent drops against account B's ids.
- The R2 PR must also rewrite the now-inverted intent comment at the largest drop site (chatLoreConfigStore.ts:684-685, "no salvage value in keeping a dangling book link").

### R3 — Per-user gated strip of `books` in hydration (backend; core; requires step-(b) frontend live — satisfied 2026-08-22)

In `list_sections` (sync.py:56-73), where every section row is already in memory (the `stm_data_bank` whole-row drop at sync.py:72 is the precedent), strip the `books` key from `stm_worldinfo`'s *payload* (shallow copy; the column is plain JSONB with no mutable wrapper and the handler never commits — but copy anyway) **iff every blob book id is accounted for without the blob**:

- **Map arm (books):** id is a key in `stm_wi_legacy_id_map.books` **and** its mapped-to UUID exists in the user's native `lorebooks` — a stale pair whose target was deleted must fail the gate, because the frontend discards such pairs (books arm, worldInfoStore.ts:2247-2251) while a shipped blob would let the heuristic re-pair against a re-import. Fold the map's target ids into the same existence query as the UUID arm.
- **UUID arm (books):** the raw id string round-trips canonically (`str(UUID(id)) == id`) **and** exists in the user's native `lorebooks`. (Not "parses as UUID": Python's `UUID()` accepts hyphenless/braced/urn/uppercase forms while lorebooks.py:936-938 stores the canonical form and the frontend resolves by string equality — a non-canonical id must count as unaccounted-for.) UUID blob ids were preserved as canonical PKs at import with no pair recorded, so map coverage can never attest for them.
- **Entry arm (every entry of every accounted book):** each blob entry id must itself be accounted — a key in `map.entries` whose target exists in the user's `lorebook_entries`, or a canonical-round-trip UUID that exists there. This arm is what makes the gate attest *content* and not just book identity; it holds the gate closed in two verified loss modes a book-only gate opens over: entries silently dropped by import validation (`_parse_blob_entry` → `None` → never inserted, never paired — see R1), and non-canonically-formatted UUID entry ids (coerced and stored canonically with *no pair recorded*, lorebooks.py:977-986 — the code's own comment concedes the equality holds only "modulo formatting"; post-strip the reference is not legacy-pattern, so R2 would not protect it, and only the blob-fed content heuristic bridges the format change, worldInfoStore.ts:2216-2232). Note the arm's feasibility rests on a verified asymmetry: entry pairs are recorded unconditionally on savepoint success (`entry_id_pairs.update` at lorebooks.py:1039) even when the *book's* id was UUID-preserved and got no book pair — so books entering via the UUID arm still have their reminted entries map-covered.
- **Degenerate ids:** a blob book whose `id` is absent, not a string, **or empty** is *skipped* (counts as accounted) — unreferenceable by construction, and holding the gate open for it would block convergence forever; same rule for id-less entries. (The empty-string case matches the import's own pair-recording predicate — its `and raw_id` guards mean a falsy id can never gain a pair, so treating `""` as checkable would close the gate permanently over a phantom.) A blob book with a missing/blank `name` is the opposite case and must stay **unaccounted**: `_extract_blob_books` skips name-less books (lorebooks.py:670-676), so it can never import and never gain a pair — a named, fail-safe, permanently-non-convergent exception (measured zero today; a future occurrence retires only via manual cleanup).
- **Defensive parse:** the gate shares only the *never-raise* property with `_extract_blob_books` — an exception here would 500 the single bulk hydration every store depends on (serverSettings.ts:127), a far bigger blast radius than the payload being trimmed. The **disposition differs deliberately**: where `_extract_blob_books` skips malformed elements so an import can proceed, the gate must treat any non-dict element or unparseable structure as *unaccounted* (fail closed) — skipping would strip a blob it couldn't fully read.

Two indexed SELECTs (`lorebooks` ids, `lorebook_entries` ids for the user), issued only when the section carries a non-empty `books` array (2 users today, decaying to zero; zero cost for everyone else). Gate fails → ship the blob exactly as today. The gate is self-arming per-user — the login that imports also records the pairs, so the *next* hydration strips — and it consults only rows in the response being built, which structurally respects first-session ordering.

Accepted non-invariants, named so nobody reopens them accidentally: the single-section `GET /sync/section/stm_worldinfo` (sync.py:76-89) and the 409 conflict payload (`current_data`, sync.py:124-130) still carry the full blob — no frontend consumer reads the section through either path (hydration is exclusively the bulk GET, serverSettings.ts:127; the 409 merge folds `current_data` into the outgoing payload only, never into client state). On the write side, `DELETE /sync/section/stm_worldinfo` remains unguarded: an explicit whole-section erase is a client-initiated act outside R1's anti-accident scope (no frontend path deletes sync sections today), as is a non-dict payload replacing the section wholesale. And a user who imports (map recorded) then deletes every native book keeps a *closed* gate under the map arm's existence check — their blob re-ships, which is the safe direction.

### R4 — ACL the map section (backend; rider on R1's PR)

`stm_wi_legacy_id_map` is server-authored but wide open: `PUT /sync/section/{name}` has no per-section guard (and `base_ts=null` bypasses optimistic concurrency entirely, sync.py:124), the create branch (sync.py:105-122) lets a client fabricate the section, and `DELETE` (sync.py:139-153) lets one erase the trail R3 depends on — unrecoverable, since pairs are only recorded at insert time. Reject client PUT and DELETE for this section (the frontend only ever reads it, worldInfoStore.ts:3465). A couple of lines, not one.

### Dropped from the draft: skip-path pair recording

The draft proposed recording book pairs on the import's matched-existing path (lorebooks.py:908-920, where the legacy id and matched server id are both in scope). All three reviewers independently converged on killing it: the skip match is (user, name, scope) equality with no content check — an *inference*, not a remint record — which is precisely the "laundering heuristic guesses into a map whose entire value is being exact" this doc rejects one section later; the frontend would bless those guesses over its own more-careful heuristic (server pairs override unconditionally, worldInfoStore.ts:2246-2251, including where the multi-book heuristic deliberately refuses ties, 2183-2213); new-wins merge semantics (lorebooks.py:800-809) plus per-login re-runs let a later wrong guess *clobber a correct insert-path pair* after a rename-and-recreate; and its beneficiary cohort is measured zero — a pre-(a) straggler with a surviving blob is *better* served by the gate staying closed (blob ships, heuristic heals) than by a name-match pair opening the strip. The map stays insert-path-only: every pair is a fact.

## Explicitly rejected

- **Server-side heuristic port** (re-derive pairs by content-signature matching over the stored blob — the plan's sketched backfill): the cohort is empty; it launders guesses into the exact map; and the frontend heuristic's known wrong-pair modes (the single-old-book path does no content check at all, worldInfoStore.ts:2180-2182) would ship server-side blessed.
- **Admin one-shot backfill endpoint** (admin_embeddings.py pattern): nothing to walk. The census *is* the walk, and it found two users whose fix is "log in" — plus a crash-safety guard to make that fix safe.
- **"Enough runway" alone** (the plan's alternative): runway doesn't converge — a permanently-dormant blob never migrates, and a global strip is never safe. The per-user gate *is* the runway argument, made per-account and mechanical.

## Test plan

Backend — R1: write omitting `books` with gate closed folds stored books back (assert row still has them); with gate open, drops them; payload carrying `books` writes through; non-`stm_worldinfo` sections untouched; no extra queries when the stored row has no `books`. R3: no map → blob ships; full book+entry coverage with live targets → stripped payload, other keys intact, stored row unmutated (re-read); map book pair with deleted target → gate closed; canonical-UUID blob book id existing natively → accounted; non-canonical UUID string (book, and separately entry) → unaccounted; **entry not covered while its book is → gate closed** (the validation-dropped-entry case: import a blob with one entry the validator rejects, assert the gate never opens); id-less book/entry → skipped; name-less book → unaccounted; malformed blob element → gate closed, no exception, hydration 200s; section without `books` → untouched, no lorebooks/lorebook_entries queries. R4: client PUT/DELETE/create of the map section rejected; import's own `_persist_legacy_id_map` path unaffected. Frontend — R2: legacy-pattern book id raw-named by the map with dead target → dropped; raw-named with live target → remapped (never reaches the drop branch); not raw-named → kept (blob present-unpaired, blob absent, and cross-user cases); legacy-pattern *entry* id raw-named with target alive in a different book → kept dangling, not dropped; native-format id behavior unchanged; raw-key sets cleared on `resetUser` (account-switch test: account A's map keys must not authorize drops after switching to account B).

Production verification (standing verify-on-production rule): the import-side half is **already verified** (2026-08-22, via the proactive import above): map rows exist with full book/entry pairs, and native entry counts match the blobs exactly (45; 10+8) — the validation-drop check passed. What remains to verify after mina or vulpixxy next actually logs in: `stm_personas`/`chatLinkedBookIds` rewritten to UUIDs, the blob retired (gate-open write or strip), and their lore fires in a real chat.

## Effort

R1+R4: one small backend PR. R2: one small frontend PR. R3: one backend PR (shares R1's gate helper). All additive; backend-first is safe for R1/R4 (pure write-path protection); R3 explicitly waits on R2 being live, and both wait on nothing else.

## Appendix — what the adversarial review changed (2026-08-22)

Three independent review lenses (data-loss interleavings, mechanism correctness, census escapes) ran against the draft, followed by a final consistency verification of the revised text. Materially: found the live blob-erasure window (now R1, the package's most urgent item — a finding about *deployed* code, not the draft); killed the skip-path pair recording (three-way convergence); promoted the drop-gate hardening from optional to core and strengthened it from "inputs available" to a per-id map-membership rule after showing the draft's condition permitted the exact drop it targeted (vulpixxy, import-failed first login) and could never handle cross-user shared-blob references; added the map arm's target-existence requirement to the R3 gate (stale pairs must fail closed); added canonical-UUID round-trip, degenerate-id, and defensive-parse rules; extended the map ACL to DELETE and the create branch; and overturned the draft's rejection of proactive import as an immediate mitigation. The review could not refute: the empty-cohort verdict itself, the first-session-ordering safety of a response-keyed gate, the Group-2 self-heal walkthrough (happy path), or the harmlessness of post-strip stale localStorage snapshots.

The final verification pass then caught and fixed three spec-level defects in the revision itself: R2 as first written was unimplementable at the resolvers (raw map keys are discarded before they run — `serverLegacyIdMap` is a `fetchPrefs` local, and target-verified filtering means a naive version degenerates to "never drop"; the spec now threads raw key sets through module state with account-switch resets, and splits the entry rule from the flat cross-book check); the shared gate attested book-id coverage but not content (validation-dropped entries — `_parse_blob_entry` → `None` — would have been erased under an open gate; the entry arm now holds it closed, and production verification counts entries before the blob retires); and the "entry-level seam cannot arise" claim was overbroad (non-canonical UUID *entry* ids get no pair and no R2 protection — same fix). It also confirmed sound: the two-call-site shared gate and its query budget, the remap-not-drop interaction, insert-path-only pair recording including the UUID-book/entry-pair asymmetry (lorebooks.py:1037 conditional vs 1039 unconditional), R4's safety, and every load-bearing citation.
